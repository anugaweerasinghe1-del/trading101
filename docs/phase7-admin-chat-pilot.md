# Admin chat pilot

The admin development desk now includes a read-only chat tab. It can offer an unverified investigation suggestion and a draft frontend change request. An owner must explicitly transfer the draft to the existing request editor, review it and submit on GitHub. The chat cannot execute code, query user records, modify its rules, approve a proposal, merge or release. It has no incident history or training mechanism yet; the separate offline memory prototype remains isolated.

## Cost and request controls

Owner-provided Google AI Studio screenshots on 2026-10-13 show project Thetradehq on Free, Gemini 3.5 Flash Lite selected, and a 500 RPD limit. The RPM/TPM red lines are below the plotted axis maxima; those maxima are not recorded as exact quota values. The small initial budget is deliberately below the shown limits: one provider attempt per UTC day across all callers, 1200 input characters, 1024 output tokens, a 30-second provider deadline, a 5-second body-reading deadline and 32 KiB response cap. The fixed system/message input is conservatively below 8192 input tokens. There are no retries, model fallbacks, grounding tools, paid services or new schedules.

This adds at most 31 provider attempts/month while enabled, approximately 254K input-token upper bound and 32K output-token upper bound. Limits are shared with other consumers in the same Gemini project; this pilot does not control course/Daily/GitHub usage. At a Pacific-day boundary, two UTC-day attempts can fall within one provider day, still far below the shown 500 RPD. Provider errors, cancellation, malformed output and safety/truncation consume the reserved attempt. Missing counters or uncertain responses deny calls. All model output remains unverified, including apparently confident statements.

The budget reuses existing `public.hit_rate_limit` with a fixed server-side subject and bucket. Its atomic SQL counter survives process restarts and concurrent requests. No migration, new grant, signing credential, billing change or production-user-data write is introduced. Metadata inspection confirmed the production table/function exist, service-role execution is allowed and anon/authenticated execution is denied. The existing database was approximately 18 MB at inspection and the connected Supabase organization is Free. Its function-invocation allowance is finite; this read-only project snapshot does not measure remaining monthly invocations. Normal pilot usage is one daily owner interaction; repeated abuse is constrained before provider calls, and Free quota exhaustion must pause operation rather than upgrade.

## Activation remains owner-controlled

The server remains paused until both secrets are configured in the existing Supabase project `cbdktpjgczhthflspqjb`:

- `TRADEHQ_ADMIN_CHAT_GEMINI_KEY`: an existing key from the verified **Thetradehq Free project**. Do not substitute a key whose project/billing origin is unknown. No fallback to another server key exists.
- `TRADEHQ_ADMIN_CHAT_FREE_REVIEW_AT`: the canonical UTC timestamp of the owner's actual billing/quota review, for example `2026-10-13T01:06:00.000Z`. The review expires after seven days, future/invalid timestamps pause calls. A timestamp records owner-reviewed configuration; it cannot independently detect an upstream billing change.

Add the key directly through Supabase's secure secret settings, never through chat, GitHub issues, browser storage or the repository. Reuse an eligible existing key; no payment method or upgrade is required. Keep billing disabled. Review again before renewing the timestamp. Owner configuration is a trust boundary: no runtime name or model allowlist alone proves a key belongs to a non-billed project. No real model call is claimed until a correctly configured owner pilot succeeds.

Like the existing owner-key admin endpoints, this new endpoint uses custom master-key authentication and a server-side global authentication budget, with `verify_jwt = false`. The frontend's publishable key is not a JWT and does not establish owner access. Handler authentication is mandatory and rejects ordinary callers before provider admission. No existing login, account architecture, endpoint protection or role grants change. The UI never persists keys/messages, displays model text as escaped text, rejects purported model authority and discards late replies after locking the workspace. Messages contain only owner-entered general website descriptions; no backend user records or logs are retrieved. Common credential/contact patterns are rejected, but pattern matching is not a complete personal-information detector. Owners must avoid private information; free-service data terms must be respected.

## Validation

`node --import tsx scripts/verify-admin-agent-chat.ts` covers authentication/configuration denial, expired review, bounded input, private-data omission, provider redirects/auth/quota/server errors, no retry/fallback, optional opaque response signatures and twelve racing requests against the existing SQL limiter with exactly one admitted provider call. All provider responses and keys are disposable fixtures; no real model is used. The AI regression suite runs it.

The existing compiled Chromium auth/Daily regression additionally tests paused chat, literal model markup, explicit draft transfer, forged merge-authority rejection and lock/late-response isolation against loopback fixtures. Chromium is unavailable in the local executor, so local browser success is not claimed; exact-head CI must demonstrate it before merge. Type checking and local agent tests pass. Production release checks and the new Edge Function must also be verified after merge. The function starts paused; activation/real-model usefulness and autonomous repair are separate capabilities, not established by this change. No maturity increment is claimed.
