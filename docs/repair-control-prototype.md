# Offline durable repair-control prototype

Status: proposed and tested locally, not installed, connected or authorized for production. The SQL lives in `docs/proposals/repair-control-prototype.sql`, outside Supabase migrations. No application, workflow or Edge Function calls it. No existing role receives a new permission. The SQL refuses to create objects without an explicit offline test setting; that setting is a mistake-prevention guard, not a security boundary against a database owner.

## Problem and scope

Stage 2 currently accepts owner-stop and attempt assertions in an offline review packet. Such inputs cannot supply durable attempt history or a server-controlled stop. This draft tests a possible private store using the existing PGlite dependency, without writing a production database or introducing a paid service.

The database now keeps an ordered, generation-bound `policy_log` of each accepted stop/resume transition, including its initial stopped state. It commits atomically with the policy update; both PGlite and disposable PostgreSQL tests check its ordering and role isolation. This is durable owner-controlled history, not a tamper-proof external audit log: a database owner could still change it. No production SQL is installed.

The prototype starts stopped, blocks missing state, serializes transitions on a policy row, and separately constrains the database to one active candidate. Claims are restricted to the existing About-page heading/layout symptom categories, one attempt per source/symptom/path fingerprint, and at most one accepted claim per rolling 24 hours. A renamed candidate cannot erase the fingerprint history. These limits are deliberately conservative; a legitimate recurring defect can remain blocked indefinitely until a separately reviewed recovery design exists. An expired claim is never automatically reauthorized. The offline prototype now offers a private, owner-operated `recover_expired` transition: it requires the exact candidate, source SHA, evidence digest and current stop generation, holds the policy lock, and only marks a claim as stopped after the database-controlled lease has expired. It retains attempt and duplicate history, issues no new claim or approval, and denies access to app roles. Owners can still use stop/resume. There is no workflow, public endpoint or production installation connected to this recovery function.

Claims bind the base SHA, evidence digest and stop generation. Validation binds one proposed head SHA. Recorded approvals expire within the claim's 30-minute lease and reject a different head, base or digest. Stop and resume increment the generation and invalidate every active claim/approval while preserving attempts and frequency history. Server time, rather than supplied client time, controls leases and expiry.

The functions use security-invoker execution, an empty search path and qualified objects. The private schema, tables and functions deny PUBLIC, anon, authenticated and service_role access, including the role that normally bypasses RLS. Tables also enable RLS without application policies. Only the database owner in the disposable test operates transitions. There is no public RPC, new role, security-definer function or permission expansion.

## Owner-signed receipt gate (offline only)

The credential-free verifier in `scripts/agent-owner-approval-offline.mjs` checks a human-signed Ed25519 receipt over candidate ID, base/head SHAs, evidence digest, stop generation and bounded expiry. Test keys are disposable; no actual owner signing identity, private key or provider credential has been added to this repository.

The offline SQL proposal now requires a 64-character receipt digest before accepting an approved review, persists the digest in candidate and transition history, and rejects missing or mismatched digests at check time. The PGlite and disposable PostgreSQL tests use a freshly verified fixture signature. The database itself cannot verify Ed25519 signatures: a trusted, owner-authenticated adapter must do so before passing the digest and expiry. Until that adapter exists, this is **not production owner authentication** and grants zero code-write or production-release authority. Imported JSON from a monitor is not sufficient to create or authorize a repair.

## What this does not prove

A recorded `validate` or `approve` transition is not independent CI evidence or verified owner identity. The store cannot establish that an About-page diff is mechanically LOW risk, that Gemini stayed within its quota, or that a Pages preview matches the proposed head. Every returned result still has `codeWrites: false` and `productionRelease: false`, including a valid review. There is no operational approval service, autonomous repair, merge or release integration.

Accepted candidates retain immutable review fields. The offline prototype also now records accepted claims, validations, approvals, rejections and expired-lease recovery in a private sequenced `transition_log` with database timestamps and exact SHA/digest/generation bindings. Candidate updates and ledger inserts share a transaction. The emergency-stop path deliberately does not depend on this ledger, and denied attempts retain bounded counters. The new ledger is not tamper-proof against the database owner and is not a complete forensic audit. Rejections and other transition outcomes use daily fixed-code counters with first/last timestamps, capped at 10,000 with explicit truncation. This avoids arbitrary input and unbounded per-request logs, but is not a complete per-event forensic audit trail. It records no user identifiers, report bodies, prompts, tokens or personal data.

The test creates and removes its own local directory, creates fixture roles locally, and applies the SQL only to PGlite. Tests cover the install guard, missing/default-stopped state, HIGH/unknown scope rejection, stale/future inputs, one active claim, SHA/digest binding, validation before approval, expiry, persistence after closing/reopening the local store, duplicate attempts, rolling limits across stop/resume, generation invalidation, audit truncation, RLS and denied application roles. PGlite queues operations on one connection: the concurrent-call fixture is not proof of real multi-session PostgreSQL behavior. A disposable PostgreSQL concurrency test remains necessary before installation.

## Approval boundary and next steps

Do not copy this file into migrations or run it against Supabase. Installation, a backend identity, grants, an authenticated owner interface and live stop operation require a separate design and explicit owner approval. Before any such approval: test real PostgreSQL locking and rollback in a disposable non-production environment; connect trusted evidence and independent validation; verify owner identity; bind approvals to the exact PR head; define complete audit retention/recovery; and preserve an independent release authorization gate. No production rollback rehearsal is authorized here.

If an installation is eventually approved, the default stopped state must remain until all integrations are demonstrated. Missing state, connection errors or uncertain evidence must deny actions. No caller may treat this prototype's booleans as permission to modify code or release.

The harness rejects every URL except the exact opt-in loopback host/port/fixture user/database/password, then verifies an empty PostgreSQL 17 database and absent fixture roles before mutations. It proves the second session is actually waiting on a policy-row lock via a third observer, verifies one accepted active candidate, serializes stop versus review, rejects replay/frequency bypass after resume and client reconnection, tests uncommitted transaction rollback and denies all application roles. Statements and lock waits are bounded. It never installs anything in Supabase. Existing PGlite tests still prove local store restart, expiry and state guards.

## Offline monitoring-to-review integration (October 11)

The new `scripts/agent-repair-pipeline-offline.mjs` invokes the **existing** `collectTrustedEvidence` verifier in diagnosis mode, not a caller-provided serialized packet. An incident is correlated with deterministic diagnosis and the existing About-page mechanical diff classifier. Even an apparently LOW change is classified as HIGH for repair admission until root cause, independent reproduction, exact-head proposal and owner identity are verified. This bounded handoff produces an evidence digest and a human investigation manifest **without creating a PR, editing source, inserting a candidate or calling Gemini**. The collector fixture tests a simulated browser incident and denies edited reports, missing attestations, stale evidence and oversized scope input.

An offline owner adapter checks injected *test-only* identity, durable policy generation/lease and Ed25519 signature/receipt binding. It always returns codeWrites/modelCalls/merge/productionRelease = false, and performs no SQL mutation. It cannot authenticate a real repository owner without an owner-configured IdP, registered public key and private service controls. Do not connect this seam to a privileged endpoint.

The GitHub main branch API reports required checks enforced for everyone; this PR remains draft and behind main. Full protection-admin read still requires additional permissions. Offline tests do not prove production repair automation.
