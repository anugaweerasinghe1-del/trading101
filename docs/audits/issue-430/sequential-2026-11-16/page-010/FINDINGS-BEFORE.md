Production application commit ad250fb272a2e5000ed6bcc4cca19b96e3efa01d and native Cloudflare deployment 3243cf7f-990c-4bd5-9392-8cd8d99dc1b9.

- **STRICT-PORTFOLIO-001 · Confirmed product defect.** With browser permission represented as granted, clicking **Alerts On** reports **Notifications Disabled** and changes the button to **Alerts**. Both mobile and desktop then deliver an in-app milestone toast and attempt an operating-system notification when the same controlled quote crosses +10%. The enabled comparison sends both as expected. The browser Notification stand-in records calls in disposable tabs. No OS notification, real account, network provider call, or external dispatch was used. Portfolio.tsx changes component state only. The guest refresh always calls checkMilestones, which unconditionally invokes the toast callback and attempts an OS notification under granted permission. [Four live browser fixture states](production-current-alerts.json)
- **STRICT-PORTFOLIO-002 · Confirmed content defect.** An unconditional Portfolio header tells the guest that “your portfolio syncs about every minute” and that the server checks supported holdings even when offline. The same guest view correctly says recovery depends on browser-held records. The snapshot requests in the fixture only read quote data. PortfolioLiveUpdates.tsx keeps guest records in their browser, while the server's scheduled held-asset queue joins persisted practice_positions. A public quote cache can include an asset also held by a guest. The server does not know a guest's local holdings from that overlap. The account-only cadence needs explicit scope.
